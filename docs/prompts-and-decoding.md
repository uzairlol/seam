# Prompts and Decoding

This chapter is a methods-section knowledge dump: the exact prompt text, the action-extraction rules, the decoding configuration, and the failure behaviour. Everything here is implemented behavior in `src/seam/agents/base_agent.py` and `src/seam/agents/decoding.py` unless explicitly labelled otherwise.

## Prompt assembly

`BaseAgent.format_prompt()` builds every prompt as a single plain-text string with six labelled sections joined by newlines. The header is `=== System ===` followed by the system prompt, whose default value is `You are a helpful, rational agent acting in a multi-agent environment.` Next comes `=== Agent ID ===` with the agent's identifier, followed by `=== Memory & Strategies ===` carrying the memory context — but only when that context is non-empty after stripping, so the segment is omitted entirely for `no_memory` agents or when the policy's `get_context()` returns an empty string. Then `=== Current Observation ===` renders the observation as the Python string representation of a dictionary (`str(observation)`), so field order and quoting in the raw string depend on the dict build order of each environment and are preserved verbatim in the logged prompt. The `=== Available Actions ===` section follows with an action-space rendering described below, and the prompt closes with `=== Instruction ===` and the trailing literal token `Action:`.

The observation/action asymmetry is important for parsing later: the environment emits observations as a plain dict, but the BargainingGame adds a `"role"` key (`proposer`/`responder`/`observer`), and it is this key that selects between three instruction templates. A `proposer` instruction states the current pie size, demands "ONLY two integers separated by a space" and explicitly forbids `accept`, `reject` or any other word; a `responder` instruction demands "ONLY the word `accept` or `reject`"; default (non-bargaining, or observer within bargaining) instructions require one of "the valid action strings". Because observers also get a generic instruction rather than an observer-specific one, the runner does not rely on the prompt to keep observers silent — it pre-selects their action as `wait` via the `default_action` parameter (see the lifecycle chapter).

## Action-space rendering

The `=== Available Actions ===` section has two mutually exclusive renderings chosen inside `format_prompt`. If the action space has more than twenty entries and its first five entries are all digit strings, the block is abbreviated to a single line `Integers from <first> to <last> (<len> choices)`. Only the NumberGuessingGame satisfies this (its action space is the integers 1 through 100), so its prompt never enumerates actions. Every other environment's action space falls to the alternative branch: a comma-space-joined list of the first twenty entries, with a literal `...` suffix appended when the space exceeds twenty entries. The ResourceForagingGame has only six actions (`stay`, `north`, `south`, `east`, `west`, and `harvest` plus coordinate forms for `move`), so all of them appear; the BargainingGame has 103 entries (accept, reject, plus all `i 100-i` splits), so its prompt lists `accept, reject, 0 100, 1 99, ...` up to the twentieth entry and then `...`. Note that the split entries are MIDI-style `"<left> <right>"` strings, so the listed `0 100` is a single action token containing a space.

## Action extraction

`BaseAgent.extract_action()` walks three detection stages in order and returns the first hit; there is no scoring or preference among multiple matches. Stage one is a case-insensitive exact match of the whole response with one of the action-space entries. Stage two scans every action-space entry as a case-insensitive regex with explicit token boundaries (`(?<![\w/])<escaped action>(?![\w/])`), which prevents substring hits such as matching `stay` inside "stationary" or `10` inside "100". Stage three, added specifically for ultimatum splits, searches for the pattern `\b(\d+)\s+(\d+)\b` anywhere in the response and, if the reconstructed candidate `"<left> <right>"` is itself an entry in the action space, returns it. If none of the three stages produces a match the function logs a warning and returns the fallback action, defined as the caller-supplied `default_action`, or failing that the first entry of the action space, or `stay` if the action space is empty.

The practical fallback flows depend on environment. In foraging, a failed extraction defaults to `stay`, the first entry. In number guessing, the first entry is `1`, so a failed extraction silently guesses `1` — the lowest guess, which is still compared against the secret and receives proper feedback. In bargaining, the first entry is `accept`; a proposer whose extraction fails therefore returns `accept`, which the environment's split parser (strict `^\s*(\d+)\s+(\d+)\s*$` plus sum-and-nonnegativity validation) fails and collapses to a 50/50 proposal. A responder whose extraction fails returns `accept` as well. Observers receive `default_action="wait"` from the runner and so fall back to `wait` first.

`BaseAgent.act()` wraps prompt building, decoding, and extraction: it builds the prompt with the current observation, action space and memory context, stores the prompt in `self.last_prompt` (which the runner later reads for event logging), computes the fallback action up front, and attempts a single completion. Any `Exception` raised in `complete()` or by an unexpected response shape is caught and also logged as an error, and the fallback action is returned. This is the only try/except boundary per agent per round; a model-level outage therefore degrades to the fallback action for the affected agents rather than aborting the episode.

## Decoding client

`OllamaClient.complete()` issues a non-streaming `generate` call to the Ollama HTTP server configured by `ModelConfig`. The options dict sent to the server is exactly `temperature` from config, `top_p` from config, and `num_predict` set to `config.max_tokens`; when `config.seed` is not `None` a `seed` option is added as well. The shipped model config `configs/model/qwen2_5_7b_instruct.yaml` sets `temperature: 0`, `seed: null`, `max_tokens: 512`, and `top_p: 1.0`, which is deterministic greedy decoding — temperature 0 makes sampling effectively greedy, and the null seed means the server is not pinned to a specific seed state. `config.request_timeout` exists in the model schema but is not currently passed into the Ollama call by the client; the field only affects nothing at runtime in the current implementation, so any paper claim about a request timeout should be checked against the client code rather than the config file.

Every completion logs model name, prompt length, response length, and wall-clock latency. Retries follow a fixed exponential-backoff schedule: attempt 1 sleeps 1 second before retry, attempt 2 sleeps 2 seconds, and so on, with at most `config.retry_attempts` (default 3, so three attempts total) before raising `OllamaClientError`. Because `BaseAgent.act()` swallows exceptions, an `OllamaClientError` surfaces in the agent as a fallback action. The client also exposes `embed()` (for embeddings) and `is_available()` / `get_model_info()` (server introspection), none of which the runner uses in the shipped pipeline.

## What reaches the log versus what reaches the environment

Two asymmetry points must be preserved when writing the methods section. First, the event log's `raw_response` field does not contain the raw model text: the runner passes the *parsed action* returned by `extract_action()`, so there is a permanent tension between the field name and its content. The original raw completion text is not persisted anywhere in the run artifacts — it exists only transiently inside `act()`. Second, the prompt stored in the event log is authoritative; it is the exact string sent to the model, captured from `last_prompt`, including any memory context and role instructions, and can be replayed or quoted in the appendix without re-running a model call.
